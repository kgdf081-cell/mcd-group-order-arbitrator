# 券池与污染商品规则（coupon-pool）

---

## 1. 随单购商品：按「麦金卡模式」决定去留

`query-meals` 里 `discountType` 含「随单购」的商品，其 `currentPrice` 是**买麦金卡之后**的价，不是普通售价。

**实测证据**：`9900011056` 全明星双人分享餐八件套
- 菜单 `currentPrice` = **49.90**
- `calculate-price`（不传 `withOrder`）= **115.50**
- 偏差 **65.60 元 / 43%**（traceId `a6ea18c8a1a38522747f4b3b93df4346`）

### 1.1 三档模式（第一步必须问用户）

| 模式 | 随单购商品 | `withOrder` | 说明 |
|---|---|---|---|
| **A 无麦金卡**（默认） | **剔除** | 不传 | 与旧版完全一致 |
| **B 已有麦金卡** | **允许入池** | **必须传**（顶层） | 金额已含卡费，见 §5.3 |
| **C 比较是否值得买** | 允许入池 | 用于算净节省 | 双次核价，见 §5.5 |

模式由用户选择，**不得替用户默认成 B 或 C**。用户没回答模式 → 按 A 处理并说明「我按无麦金卡算的」。

**不存在**「先按 A 算，超预算再偷偷加 `withOrder`」这种中间态——那会让报价在演示中途跳变。

### 1.2 只有模式 A 才允许剔除

模式 B / C 下如果把随单购商品剔掉，就等于把用户已经付费的权益丢掉，**比算错价更严重**：用户会觉得「我明明有卡，你为什么给我看更贵的价」。

## 2. 券池

### 2.1 券和菜单不重合

`query-store-coupons` 返回的 `products[].productCode` **可能不在** `query-meals` 的 SKU 列表里。

实测：`9900004002` 麦辣鸡腿堡3件套只出现在券池，菜单 130 个 SKU 里没有它。

**所以必须单独建券池**，不能指望从菜单里扫到。

### 2.2 券调用的完整参数

```
calculate-price
{
  "storeCode": "<动态获取>",
  "orderType": 1,
  "beType": 1,
  "items": [{
    "productCode": "9900004002",
    "couponId":    "<query-store-coupons 返回>",
    "couponCode":  "<query-store-coupons 返回>",
    "quantity": 1
  }]
}
```

- `item` 里必须有 4 个字段：`productCode` / `couponId` / `couponCode` / `quantity`
- 外层必须有 `storeCode` / `orderType` / `beType`
- **不传 `beCode`**（`beType: 1` 的门店不需要）
- 有 `roundList` 时放在 `item` 内

### 2.3 三条硬约束（全部实测确认）

**① 一券一份**

传 `quantity: 2` 时，接口**不报错**，静默返回 `quantity: 1`（traceId `28fc879b...b924`）。
对照组：普通商品 `1100` 传 `quantity: 2` 正常返回 2 份（traceId `2de78470...8ac5`），排除「接口不理数量」。

→ 规则：`Σ(使用 couponId X 的成员数) ≤ 1`

**② 裸算为空单**

券商品不带券：`price: 0`、`productList: []`，接口**不报错**（traceId `2e49e6b5...b99e`）。
若求解器不校验，会把它当「0 元免费商品」算出荒谬的最优解。

→ 规则：`productList` 为空 或 `price === 0` 一律判无效。

**③ 券商品零替换自由度**

`9900004002` 的详情（traceId `ef2c0990...d1c4`）3 个 round **各只有 1 个 choice**，无任何替换项。

→ 规则：不要给券商品编造替换项；它的价值就是「便宜 + 不可调」。

## 3. 券的可用性判断顺序

```
1. query-store-coupons 拿到券列表
2. 丢弃 tradeDateTime 已过期的券
3. 逐张带券核价（一次一张），确认 price > 0 且 productList 非空
4. 打辣度标签（券商品同样走 risk-glossary）
5. 进入候选池，标注「券 ×1」
```

**第 3 步不能省。** 券列表说可用，不等于算价能生效。

## 4. 麦金卡与 `withOrder`（模式 B / C 专用）

> 完整实测见 `demo/membership-probe-20261025.md`。本节只写规则。

### 4.1 参数位置（唯一正确写法）

`withOrder` 是 `calculate-price` 的**顶层参数**，与 `items` **同级**：

```json
{
  "storeCode": "<动态获取>",
  "orderType": 1,
  "beType": 1,
  "withOrder": {
    "membershipCode":   "<query-meals → meals[code].withOrder.membershipCode>",
    "membershipSpecId": "<query-meals → meals[code].withOrder.specId>"
  },
  "items": [
    { "productCode": "<随单购商品>", "quantity": 1 }
  ]
}
```

三条不可违反：

1. **`withOrder` 必须在顶层。** 放进 `items[]` 会被**静默忽略**，返回普通价且不报错（traceId `9bd30d9c752512109bb0f6b3bbd02a6c`，`price` 11550 而非 5980）。
2. **`specId` 必须改名为 `membershipSpecId`。** 这是唯一允许的字段重命名。两个值都必须从 `query-meals` 的 `withOrder` 对象**实时读取**。
3. **禁止硬编码 `membershipCode` / `membershipSpecId` / `storeCode`。** 卡种与规格随门店和活动变化。

> 已知但**不采用**的写法：只传 `membershipCode` 也能生效（traceId `2eb034e3…5024`），传 `specId` 原名也生效（`22d36fec…ec97`）。
> 这两种都是文档未记载的宽松兼容，**不要依赖**——换店或换活动可能失效。只传 `membershipSpecId` **不生效**（`ac31827a…c17d`），且不报错。

### 4.2 卡费是 `productList` 里的独立一行

带 `withOrder` 核价后，`productList` **会多出一行卡片商品**（本店为 `521234` 麦金卡体验卡（15天），`subtotal 990`）：

```
9900011056  全明星双人分享餐八件套  ×1   subtotal 4990
521234      麦金卡体验卡（15天）      ×1   subtotal  990
price 5980   originalPrice 12540   discount 6560
```

- **卡费必须从 `productList` 里识别出来**：`productCode` 不在请求的 `items` 里、且 `subtotal > 0` 的那一行
- **卡费按单收一次**，与随单购商品个数、`quantity` 都无关（实测：同商品 ×2、或两个不同随单购商品，卡行 `quantity` 仍为 1）
- 菜单上的 49.90 既不是无卡价（115.50），也不是实付（59.80）

> **`521234` 只是这一家店在 2026-10-25 的卡编码，不得写死。**
> 判断依据只能是「不在 `items` 里且 `subtotal > 0`」，不能靠编码匹配。换门店、换档期卡种就会变。

### 4.3 三个静默陷阱（都不报错）

| 现象 | 后果 | 防御 |
|---|---|---|
| `withOrder` 放 `items[]` 内 | 返回普通价，看起来「卡没用」 | 传参前断言 `withOrder` 在顶层；核价后断言「卡行存在」 |
| 订单里没有随单购商品却传了 `withOrder` | 商品零折扣，**卡费照收 ¥9.90** | 传 `withOrder` 前必须确认 `items` 中至少一个商品的 `withOrder` 非空 |
| 只传 `membershipSpecId` | 完全不生效 | `membershipCode` 视为必填 |

### 4.4 与券可同单并存

券 + 随单购在同一次核价里**互不冲突**，两者可同时生效（实测 `8270 = 4990 + 2290 + 990`，traceId `4cdb52c6c154dd4ded6377d74e718938`）。

→ 模式 B 下仍需执行 §2.3 的「一券一份」与「空单防御」，两套规则叠加，不互相豁免。

### 4.5 模式 B 的额外校验（在 `fairness.md` §8 之上）

- [ ] 请求里 `withOrder` 位于顶层
- [ ] `withOrder` 的 `membershipCode` / `membershipSpecId` 可在本次 `query-meals` 返回中溯源
- [ ] `items` 中至少一个商品的 `discountType` 含「随单购」
- [ ] `productList` 中存在卡行，且卡行 `quantity === 1`
- [ ] `price === Σ(商品行 subtotal) + 卡行 subtotal`（卡费已计入，不是在总价之外）
- [ ] `discount > 0`（若 `discount === 0`，说明 `withOrder` 未生效，方案作废）

> 最后一条是模式 B 的**兜底断言**：没有折扣却带卡费，等价于「多花了 9.90 什么都没换到」，必须整单作废而不是照常输出。

## 5. 模式 C · 是否值得买卡

### 5.1 能算的部分

MCP **没有**麦金卡价格/权益查询工具，`query-my-account` 只返回积分，不返回会员卡状态。
但卡费本身**可以从 `productList` 读出来**（本店 `521234` 麦金卡体验卡 15 天 / ¥9.90）。

所以模式 C 只做一件事：**对同一份订单做双次核价，比较净节省**。

```
对每个含「随单购」商品的候选组合：
  P_no  = calculate-price（不传 withOrder）        → 无卡实付
  P_yes = calculate-price（传 withOrder）          → 含卡实付
  C_card = P_yes 的 productList 里卡行的 subtotal   → 卡费
  P_meal = P_yes − C_card                          → 带卡餐费
  Save   = P_no − P_meal                           → 餐费节省
  Net    = Save − C_card                           → 净节省
```

只有 `Net > 0` 才可以说「这一单买卡划算」。

### 5.2 必须说的三句话

1. **卡种要说清**：是「麦金卡体验卡（15天）¥9.90」，不是「麦金卡」。
2. **范围要说清**：「仅本次订单」——接口无法模拟卡在有效期内跨单使用，所以不能算 15 天累计收益。
3. **结论要设限**：「在本次核价的 N 个候选内，买这张体验卡净省 ¥X」；不得说「办卡一定划算」。

### 5.3 卡费算不出来时怎么办

如果 `productList` 里**找不到**卡行（`price` 不含卡费，或接口改版），则：

> 「当前无法计算买卡是否划算：接口没有返回这张卡的价格，只给了会员价。
> 我可以按『已有麦金卡』给你算餐费，但那不代表买卡值得。」

**禁止**只展示会员价、把差额当收益。也**禁止**替用户判断「你应该办卡」。

### 5.4 绝不代买

模式 C 只做比较，**不调用任何下单接口**，不自动购买麦金卡，也不创建订单。

## 6. 输出措辞

- ✅「本次券池中有 1 张可用券，带券实付 22.90 元」
- ❌「该店最低套餐 22.90 元」（未穷尽比较，不能这么说）
- ✅「券商品仅 1 份可用，本方案分配给了 C」
- ❌「每人一份券套餐」（违反一券一份）

模式相关的措辞：

- ✅「模式 B · 已有麦金卡：金额 **135.30** 元，**已包含麦金卡体验卡（15天）¥9.90**」
- ✅「若你已持有有效麦金卡、无需再买这张卡，实际可能少付 ¥9.90，但接口无法验证 —— 本金额可能高估」
- ✅「模式 C · 仅本次订单：买这张 ¥9.90 体验卡净省 ¥55.70。不能据此判断办正式会员是否划算」
- ❌「会员价 49.90 元」（这是含卡后的餐价，不是实付）
- ❌「有麦金卡就便宜 65 块」（漏掉卡费，且只对单件商品成立）
- ❌「建议你办一张麦金卡」（不替用户做消费决策）

券凭据（`couponId` / `couponCode`）在公开材料中一律脱敏为 `B7A9...FEC5` 形式。
