# 麦门拼单官 · mcd-group-order-arbitrator

> 四个人一起点麦当劳，最难的从来不是「吃什么」，是「谁都不想吃亏」。
>
> 这个 Skill 把「公平」变成一道能算、能复核、能被推翻的题：给出三套可比方案。**两套最终方案的展示金额均来自官方算价接口；菜单价只用于候选初筛，每一处「未知」都明确标成未知。**

一个基于**麦当劳官方 MCP** 的多人拼单仲裁 Skill。

> **适用范围**：规则与算法（`src/rules/`）是纯文本逻辑，可迁移到任何能调用 `mcd-mcp` 的宿主。
> 但**安装方式、Skill 加载机制和录屏证据目前只针对 WorkBuddy 验证过**，其他 MCP 客户端未做实测，不承诺开箱可用。

---

## 它解决什么问题

多人拼单有四个真实痛点，市面上的「推荐助手」基本都没处理：

| 痛点 | 具体表现 | 本项目的处理 |
|---|---|---|
| **忌口是硬约束，不是偏好** | 有人说「不吃辣」，助手推了个麦辣鸡腿堡 | 辣度分四档，无信号一律判「未知」，绝不写成「不辣」 |
| **菜单价不是实付价** | 菜单标 49.9，实付 115.5 | 排序只用 `calculate-price` 返回值，菜单价仅初筛 |
| **「公平」没有算法** | 最后变成「大概差不多吧」 | minimax 个人牺牲分，公式可复算，附算例 |
| **有券不等于便宜** | 券 22.9，普通套餐 20.5 | 券不预设优先级，和普通商品一起比实付 |

## 安装

### 1. 拿 Token

到 [open.mcd.cn/mcp](https://open.mcd.cn/mcp)，手机号登录后在控制台激活领取，免费。

### 2. 配置 MCP

把 `mcp-config.example.json` 的内容合并进 `~/.workbuddy/mcp.json`，**并把 `${MCD_MCP_TOKEN}` 手动替换成你自己的真实 Token**：

> ⚠️ **`${MCD_MCP_TOKEN}` 只是占位符，不是变量引用。**
> 本项目**未验证** WorkBuddy 会自动展开环境变量，也没有在 `mcp.json` 里实测过 `${...}` 语法。
> 最稳妥的做法是直接把这一串替换成真实 Token 字符串再保存。请不要提交带真实 Token 的 `mcp.json`。

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": { "Authorization": "Bearer ${MCD_MCP_TOKEN}" }
    }
  }
}
```

在 WorkBuddy 的「自定义连接器」里启用 `mcd-mcp`。

### 3. 安装 Skill（**要装整个目录**）

算法和规则都在 `rules/` 里，**只复制 `SKILL.md` 会导致 Skill 读不到规则、直接拒绝执行**。

```bash
git clone https://github.com/<你的用户名>/mcd-group-order-arbitrator.git
cd mcd-group-order-arbitrator

mkdir -p ~/.workbuddy/skills/mcd-arbitrator
cp -R src/. ~/.workbuddy/skills/mcd-arbitrator/

# 校验完整性（必须无输出）
diff -r src ~/.workbuddy/skills/mcd-arbitrator
```

Windows：

```bat
xcopy /E /I src "%USERPROFILE%\.workbuddy\skills\mcd-arbitrator"
```

安装后结构：

```
~/.workbuddy/skills/mcd-arbitrator/
├─ SKILL.md
└─ rules/
   ├─ fairness.md        公平算法、三套方案目标函数、校验清单
   ├─ risk-glossary.md   辣度四档与证据分级
   ├─ coupon-pool.md     券池规则、随单购黑名单
   └─ pipeline.md        六步流程的精确参数与调用预算
```

## 使用示例

在 WorkBuddy 里说：

> 用麦门拼单官帮我拼单。南京软件谷，4 个人，总预算 150。
> 小林不吃辣，想吃鸡肉，最多 40；小周想吃牛肉、要可乐，45；
> 小陈只要薯条，预算 30；小王想吃鸡翅，40。

Skill 会走完六步（定门店 → 建池 → 取套餐结构 → 生成候选 → 核价 → 输出），中间会主动问一句：

> 「板烧鸡腿堡的辣度官方数据里查不到。你之前吃过吗？如果确认没问题，我按『你已确认』处理，并在结果里标注这是你的确认，不是官方数据。」

**这一步不能省。** 它是「未知」唯一合法的放行通道。

## 它和别的点餐助手有什么不同

### ① 辣度不撒谎

MCP 没有辣度字段。所以：

| 档位 | 判定 | 能否进入「已满足」 |
|---|---|---|
| 高 | 命中「麦辣 / 川香 / 龙焰 / 椒盐 / 藤椒 / 韩式辣椒」 | ❌ |
| 疑似 | 命中「黑椒 / 奥尔良 / 卡真 / 咖喱」 | ❌ |
| **未知** | **无任何辣度信号（占绝大多数）** | ❌ |
| 用户确认 | 用户本人说吃过、没问题 | ✅ 仅对该成员该商品 |

**没有「低风险」这一档。** 名字里没有「辣」字，只能推出「未知」，推不出「不辣」。

还有一个反直觉的点：**「去酱」不等于「去辣」**。麦辣鸡腿汉堡的特调只能去麦香鸡酱和生菜，辣味来自腌料。

### ② 价格只用官方算价

实测算过一笔账：`9900011056` 全明星双人分享餐八件套，菜单标 **49.90**，不买麦金卡直接核价是 **115.50**——差 65.6 元，菜单价只有实付价的 43%。

这类「随单购」商品在本店有 15 个。所以 Skill 硬规则第 2 条：`discountType` 含「随单购」的商品**直接不进候选池**。

### ③ 公平是可复算的

```
S_m(x) = Σ_{未满足的偏好} w(p)  +  0.2 × max(0, 该成员正差价之和) / 10
```

权重固定：指定单品 4、指定品类 3、指定饮品/做法 2、附加小食 1。正差价按每 10 元 0.2 分折算，负差价不算牺牲。

每套方案都输出 `max S` 和 `Σ S`，任何人都能拿计算器复核。

### ④ 会拒绝给方案

这是最难做对的一步。只要模型偷懒，「未知」就会被悄悄当成「不辣」，然后输出一个看起来完美、实际有风险的方案——**而且它不会报错**。

所以 `demo/honest-exit-20261024.md` 专门留了回归证据：去掉用户确认后，Skill 必须拒绝输出严格方案。

## 实测发现的 5 个接口陷阱

这些都在 `demo/mcp-probe-20261024.md` 里有 traceId 可复现：

| # | 陷阱 | 现象 |
|---|---|---|
| 1 | 随单购虚假低价 | 菜单 49.9 → 实付 115.5，差 43% |
| 2 | 一券一份 | 传 `quantity: 2`，静默返回 1 份，**不报错** |
| 3 | 空券空单 | 券商品不带券 → `price: 0`、`productList: []`，**不报错** |
| 4 | 套餐子项不回显 | 带 `roundList` 时只返回父套餐，无法逐项校验 |
| 5 | 同价替换 | 可乐 / 无糖可乐 / 雪碧 `diffPrice` 全为 `+0`，替换被忽略时总价相同 |

第 2、3 条的 HTTP 状态码都是 `200`。**只看状态码或 `success: true`，这两个陷阱会直接进方案。**

## 已知限制

1. **求的是有限搜索解，不是全局最优。** 只对「菜单初筛 → 5 个模板 → top 3–5 候选核价」的范围内求解。输出里一定带「本次已搜索、已核价的 N 个候选内」。
2. **套餐子项无法独立确认。** 接口不回显，只能验证「请求选项来自套餐详情」+「金额与预期一致」。金额相同是**必要非充分**条件（见陷阱 5）。
3. **辣度是风险分层，不是安全证明。** 不做任何「不辣」承诺。
4. **过敏原完全不做判断。** MCP 无配料数据，统一提示「请到店确认」。
5. **不自动下单。** 只做核价，不调 `create-order`。
6. **门店动态查询。** 不硬编码 `storeCode`；演示用店只是「预选」，不是唯一。
