## 结论先写

| 问题 | 能否回答 | 结论 |
|---|---|---|
| 「这一单买这张卡值不值」 | ✅ 能 | 净省 ¥55.70 / ¥19.60（两个样本） |
| 「办正式麦金卡划不划算」 | ❌ **不能** | **当前无法计算买卡是否划算** |
| 「我已经有卡了，还要付 9.90 吗」 | ❌ **不能** | 接口无法验证持卡状态 |

**因此模式 C 的输出必须两句都写**：本单净省多少 + 正式会员问题无法计算。
只报「净省 ¥55.70」而不说清边界，等于把「一张 15 天体验卡回本」偷换成「办会员划算」。

## 1. 能算的部分：同一订单双次核价

```
P_no   = calculate-price（不传 withOrder）
P_yes  = calculate-price（传 withOrder）
C_card = P_yes.productList 中卡行的 subtotal
P_meal = P_yes − C_card
Net    = P_no − P_meal
```

> **口径声明**：下列 `P_no` 均来自**单品**无卡核价（`items` 里只有该商品 1 项），
> 不使用任何多商品整单的 traceId 去代表单品价格。
> 单品核价于 2026-10-25 14:51 现场补跑，与同一商品在整单中的小计一致。

## 2. 查不到的部分（逐条实测）

### 2.1 卡能不能单独核价 → 不能

```json
{"items": [{"productCode": "521234", "quantity": 1}]}
```

```json
{"success": false, "code": 60006,
 "message": "商品已售罄或不可售，换一个商品或检查orderType/beType",
 "traceId": "a017bb878612243213f72343e8935405"}
```

**卡只能在 `withOrder` 生效时作为附加行出现，不能独立购买核价。**

### 2.2 卡有没有结构化详情 → 没有

```json
{"code": "521234", "storeCode": "1990583", "orderType": 1, "beType": 1}
```

```json
{"code": 200, "traceId": "429b651483f52196130ac9f3390348c9",
 "data": {"code": "521234", "name": "麦金卡体验卡（15天）", "rounds": [], "supportModify": false}}
```

只有名称，**无价格、无有效期字段、无权益字段**。
「15 天」只存在于商品名字符串里，**不能当结构化条件使用**。

### 2.3 用户是否已持卡 → 查不到

```json
{"tool": "query-my-account", "params": {}}
```

```json
{"code": 200, "traceId": "d4ae95616984c724c39d10d6a8ee8d6d",
 "data": {"accountId": "0200…914", "availablePoint": "23.9",
          "accumulativePoint": "23.9", "currency": "麦享会积分"}}
```

只有积分字段，**没有任何会员卡状态/等级/有效期**。
→ 无法回答「我已持卡，这 9.90 还要不要付」。

### 2.4 正式麦金卡的价格/权益 → 查不到

`mall-points-products`（`catRuleIds: "1>4,2>9"`，商品券 + 实物礼品卡）返回 **24 个积分商品**，全部是餐品券（`16.9元2杯麦辣鸡翅`、`10.9元指定小食任选` 等），**没有麦金卡**。

```json
{"code": 200, "traceId": "6e209679f9dc892fe2591ab36293215b", "data": [ ...24 项... ]}
```

### 2.5 团餐促销接口 → 场景不适用

`query-promotions` 只支持 `beType=6`（企业团餐）+ `orderType=2`（外送），与到店单人/多人场景不匹配，**未调用**。

## 3. 必须原样输出的话术

用户问「办麦金卡到底划不划算」时：

> 「**当前无法计算买卡是否划算。**
> MCP 查不到正式麦金卡的价格、权益和有效期，也查不到你是否已持有。
> 我能算的只有这一单：卡费 ¥9.90（从返回明细里读到的，不是菜单价），
> 餐费从 ¥115.50 降到 ¥49.90，整单净省 **¥55.70**。
> 这只能证明这张 15 天体验卡**在这一单上**回本，不能推出办会员划算。」

用户问「我已经有卡了」时：

> 「接口无法验证你的持卡状态。按带卡核价，订单里会出现一行 ¥9.90 的『麦金卡体验卡（15天）』。
> 如果系统识别到你已有有效卡、不再收这 9.90，实际会比我报的少 ¥9.90。
> 我报的金额**可能高估**，不能保证是你最终要付的钱。」

**禁止**：
- ❌ 只展示 ¥59.80 / ¥49.90 的会员价，不提卡费
- ❌ 把「本单净省 ¥55.70」说成「办卡能省 ¥55.70」
- ❌ 推算「15 天能省多少」（接口无有效期字段，无法验证跨单使用）
- ❌ 建议用户「你应该办卡」
- ❌ 调用 `create-order` 或任何购买麦金卡的接口

## 4. 模式 C 的输出格式（首行固定）

```
模式 C · 比较是否买卡（结论仅限本次订单）
```

然后三行：

1. 本单：无卡 ¥115.50 → 带卡 ¥59.80（含卡费 ¥9.90），净省 **¥55.70**
2. 边界：15 天有效期来自商品名，接口无结构化有效期；跨单收益无法验证
3. **正式会员是否划算：当前无法计算**

## 5. 与需求的偏差说明

原需求要求「只有在 MCP 能查到麦金卡实际购买成本和有效条件时才计算」，否则提示无法计算。

实测结果是**一半一半**：

- 购买成本 ✅ 能从 `productList` 卡行读到（¥9.90）
- **有效条件 ❌ 查不到**（无结构化字段，仅商品名含「15天」）
- 持卡状态 ❌ 查不到

所以实现为：**单笔订单层面计算净节省（成本和餐费都可验证），但对「办会员是否划算」严格拒绝**。
这样既没有夸大（不回答长期问题），也没有装死（单笔可算的照算）。
用户若要求「只回答长期问题」，则整段回退为「当前无法计算买卡是否划算」，不展示任何会员价对比——避免只给会员价造成误导。
