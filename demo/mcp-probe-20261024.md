## 5. 算价（`calculate-price`）四组实验

### 5.1 基础单品 —— 单位与名称

```json
{"storeCode":"1990583","orderType":1,"beType":1,
 "items":[{"productCode":"1100","quantity":1},
          {"productCode":"4810","quantity":1},
          {"productCode":"9900008751","quantity":1}]}
```

巨无霸 2650 + 中薯条 1400 + 可乐 950 = **5000 分 = 50.00 元**，`discount: 0`。

- 单位确认为**分**，展示 ÷100。
- 同一商品两接口名称不一致：`薯条`（菜单）→ `中薯条`（算价）。**输出以算价为准**。
- 返回 `takeWayList: [eat-in 堂食, take-in-store 外带]`。

### 5.2 随单购套餐 —— 菜单价失真

`items:[{"productCode":"9900011056","quantity":1}]`，不带 `withOrder`：

| 数据源 | 金额 |
|---|---|
| 菜单 `currentPrice` | 49.90 |
| 算价实付 | **115.50** |
| 偏差 | **65.60 元（43%）** |

原始字段 `discountType: "随单购麦金卡优惠"`，`withOrder: {membershipCode:"106", specId:"880"}`。

受污染商品（实测清单，均含 `随单购` 标记）：`9900011056` 49.9/115.5、`9900004236` 28/57.5、`9900010110` 32/59、`9900006957` 37/66.5、`9900000881`/`0882`/`0885`/`0886`/`0888`/`0893` 32–37/59–66.5、`9900000884` 28/55.5、`9900000891` 28/57.5、`9900016309` 29/57.5、`9900005321` 62.9/123、`510479` 9.9/23。

### 5.3 券商品 —— 一次性，且裸算无效

**带券 ×1**：原价 4650 → 实付 **2290 分 = 22.90 元**，`discount: 2360`。

三组对照：

| 实验 | 请求 | 返回 | 判定 |
|---|---|---|---|
| A | `1100` ×2，无券 | `quantity:2`, `price:5300` | 接口数量处理正常 |
| B | `9900004002` ×2，**带券** | `quantity:1`, `price:2290` | **数量静默回落为 1** |
| C | `9900004002` ×2，**无券** | `price:0`, `productList:[]` | **静默空单，不报错** |

A 排除「接口不理数量」的可能，因此 B 属券本身限制：**一个 `couponId` 只能兑换 1 份**。

> 表述修正：**本次实测返回的券中**，麦辣鸡腿堡三件套算价为 22.90 元，是本次样本中最低的完整套餐。
> 不等于「该店最低」——未对全部可售商品与优惠做穷尽比较，不作此断言。

### 5.4 套餐 roundList —— `diffPrice` 真实可加（决定性验证）

`query-meal-detail` 对 `9900005466` 巨无霸三件套返回 3 轮：

| Round | 名称 | 默认 | 候选（含差价） |
|---|---|---|---|
| 1 | 新升级巨无霸 | `1100`（可特调） | 单一 |
| 2 | 套餐内小食 | `4810` 中薯条 +0 | 心形薯饼+辣酱 +1 / 大薯 +2 / **小杯玉米杯 −1** / 大杯玉米杯 +1.5 / 脆脆薯条 +2 |
| 3 | 套餐内饮料 | `3050` 可乐中杯 +0 | 无糖可乐 +0 / 雪碧 +0 / 柠檬红茶 +0 / **纯牛奶 +0.5** / 锡兰红茶 +1 / 苹果汁 +1.5 / 茉莉奶绿雪冰 +3 / 冰美式 +9 / 热浓浓黑巧 +11 |

**算价实证**（参数格式：`{"round":"1","comboItemList":[{"code":"1100","quantity":1}]}`，`round` 传数字字符串）：

| 配置 | 请求 roundList | 实付 | 对基线 |
|---|---|---|---|
| 默认 | 1100 / 4810 / 3050 | **3750 分 = 37.50** | 基线 |
| 换纯牛奶 | 1100 / 4810 / **3755** | **3800 分 = 38.00** | **+0.50** ✅ |
| 换玉米杯+纯牛奶 | 1100 / **4437** / **3755** | **3700 分 = 37.00** | **−0.50** ✅ |

**结论：`diffPrice` 是可加的真实金额，正负差价均精确落地。**

**但有一条关键限制**：带 `roundList` 时，`productList` **只返回父套餐** `9900005466`，子项（1100 / 4810 / 3755）**完全不出现**。
→ 子项无法做「逐项出现」校验，只能做**总价等式校验**（见 §7）。

### 5.5 特调（modification）

Round 1 的 `1100` 支持特调，可取消：巨无霸酱、吉士、生菜、酸黄瓜、洋葱粒（`maxValues:5, minValues:0`），每组带 `selectedKey:"0-1"` / `unselectedKey:"0-0"`。

> 去酱 **≠** 不辣（辣味可能来自腌料），输出须说明这一限制。

## 6. 券的三条硬约束

1. **一券一份**：`Σ(使用 couponId X 的成员数) ≤ 1`。
2. **空单防御**：`productList` 为空或 `price===0` 一律判无效，禁止当 0 元参与比价。
3. **券商品详情可查，但灵活性远低于普通套餐**（v1 曾推断「不可查」，已由 #15 实测推翻）：
   - `9900004002` 详情正常返回，3 个 round 各**只有 1 个 choice**，无任何替换项；
   - 唯一可调的是特调：麦辣鸡腿汉堡可去「麦香鸡酱」「切块生菜」，可乐可改冰量；
   - **没有「去辣」特调**——辣味来自腌料，去酱不等于不辣。

> 因此券商品 = 低价 + 零替换自由度。**不能给它做「换饮料」优化，也不要把「去酱」当成降辣手段。**

## 6c. 补充实测：同价替换是子项校验的关键漏洞（#19）

`9900004835` 的 round 3 中，以下选项 `diffPrice` **全部为 `+ ¥0`**：

`3050` 可乐中杯 · `3071` 无糖可口可乐中杯 · `3060` 雪碧中杯 · `515281` 阳光柠檬红茶中杯

**含义**：如果把可乐换成无糖可乐，请求被服务端忽略（仍按可乐出单），**总价完全相同**，金额等式校验照样通过。

→ **金额等式是必要非充分条件。** 子项校验必须再加一段「请求侧来源校验」（`round` id、`code` 必须逐项来自该模板详情的 `choices[].code`），否则无法排除静默忽略。完整规则见 `src/rules/fairness.md` §8.2。

## 7. 异常校验规范

### 7.1 顶层商品（可逐项校验）

对请求中每个顶层 `productCode`：
- [ ] 必须出现在返回 `productList` 中
- [ ] `productList[].quantity` 必须等于请求 `quantity`
- [ ] 券商品的 `productCode` 必须与 `query-store-coupons` 的 `products[].productCode` 匹配，且请求同时携带匹配的 `couponId` + `couponCode`
- [ ] 返回 `price > 0`

任一项不满足 → **整套方案作废**，不得仅对该项降权。

### 7.2 套餐子项（接口不回显，只能两段校验）

**接口事实**：带 `roundList` 时 `productList` 只返回父套餐，子项完全不出现。因此**无法独立确认服务端实际采用的全部选项**，这是接口能力边界，不是校验宽松。

**第一段 · 请求侧来源校验**

- [ ] `roundList[].round` == 该模板详情的 `rounds[].id`
- [ ] `comboItemList[].code` 逐项存在于该 round 的 `choices[].code`
- [ ] 选项个数满足该 round 的 `minQuantity ≤ n ≤ maxQuantity`
- [ ] `diffPrice` 与详情一致

**第二段 · 金额等式（适用范围严格限定）**

```
实际 price == 基准价 + Σ diffPrice(替换项)
```

实测校准：`37.50 + 0.50 = 38.00` ✅、`37.50 − 1.00 + 0.50 = 37.00` ✅

⚠️ **仅在「整单只有 1 个套餐、不带券、`discount == 0`、无其他优惠」时成立。**
多套餐 / 带券 / 有满减时，整单实付与单个套餐基准价之间**不存在**该等式关系，只能做 §7.1 加第一段。

### 7.3 为什么必须逐项而非整体

一张无效券商品可能被服务端静默丢弃，而订单里还有其他有效商品，此时 `productList` 仍非空、`price` 仍 > 0。
只看整体非空会漏判 → 必须逐项比对。

### 7.4 输出必须附带的限制语

> 「算价接口不回显套餐子项，我们只能验证『请求的选项来自套餐详情』且『金额与预期一致』，**无法独立确认服务端实际采用的完整选项**。」

## 8. 复现方式

```
1. WorkBuddy 启用 mcd-mcp（Streamable HTTP + Bearer <TOKEN>）
2. query-nearby-stores  {city:"<城市>", keyword:"<商圈>", searchType:2, beType:1}
3. query-meals         {storeCode, orderType:1, beType:1}
4. query-store-coupons {storeCode, orderType:1, beType:1}
5. query-meal-detail   {storeCode, orderType:1, beType:1, code}
6. calculate-price     {storeCode, orderType:1, beType:1, items:[...]}
```

零本地依赖，任意支持 MCP 的客户端可复现。
